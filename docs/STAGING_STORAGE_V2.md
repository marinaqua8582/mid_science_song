# 학생별 저장 소유권 (staging 전용 검증 단계)

기존 staging 25명 시험은 로그인 25/25 성공 후 1단계 저장 6/25 성공, 503 19건이었다. 전체 저장 구간을 ScriptLock으로 직렬화한 것이 병목 가설이다. 아직 수정 버전의 실제 25명 재시험은 하지 않았다.

## 저장 흐름

- 전역 ScriptLock은 유지하며 기존 8초 대기 시간을 늘리지 않는다. 잠금 안에서는 ScriptProperties의 학생별 소유권과 고유 행 번호 예약만 수행한다. Sheets 호출과 캐시 갱신은 하지 않는다.
- 동일 학생은 한 실행만 소유한다. 다른 학생은 다른 행을 소유하므로 Sheets I/O를 동시에 수행할 수 있다. CacheService를 잠금으로 사용하지 않는다.
- 예약 행 번호는 PropertiesService에 영속화한다. 카운터를 먼저 증가시켜 중간 실패 시 빈 행은 생길 수 있어도 다른 학생에게 같은 행 번호를 할당하지 않는다. 매 저장의 appendRow/getLastRow/전체 인덱스 재생성을 없앤다.
- 데이터와 requestId/hash/savedAt 저널은 한 setValues에 포함한다. 해당 학생 소유권을 유지한 상태에서 한 번 flush하고 그 뒤에만 성공 응답을 반환한다. flush는 전역 잠금 밖이다. 이는 Google의 [flush 후 소유권 해제 지침](https://developers.google.com/apps-script/reference/lock/lock)을 학생별 소유권에 적용한 것이다.
- 재전송은 기존 저널을 검사하고 같은 requestId의 다른 payload는 REQUEST_ID_CONFLICT로 거부한다. 저널의 100개 보존 및 cutoff 보호는 유지한다.
- 행 키 또는 저널 헤더가 바뀌면 STORAGE_LAYOUT_CONFLICT로 중단한다. 실행 중 행 정렬·삽입·삭제와 동시 수동 편집은 지원하지 않는다. 자동 재인덱싱으로 다른 학생 행을 덮어쓰지 않는다.

## 테스트 GAS 배포 순서

1. 알려진 별도 테스트 Sheets만 읽기 전용으로 내보내 기존 6개 행의 중복·payload·저널을 검사하고 보존한다. 운영 데이터는 조회하지 않는다.
2. 테스트 프로젝트의 Code.gs만 교체하고 저장한다. 기존 웹 앱을 새 버전으로 갱신하여 URL/테스트 비밀값을 유지한다. 운영 GAS는 변경하지 않는다.
3. 요청이 없는 상태에서 편집기의 `prepareSubmissionStorage`를 한 번 실행한다. 기존 행/저널을 보존하고 중복·불완전한 키가 있으면 중단한다. 학생 행은 추가/삭제하지 않는다. 준비가 없으면 요청은 STORAGE_NOT_READY로 실패한다. 재실행은 이미 준비됨으로 반환하며 소유권을 지우지 않는다.
4. 지정 브랜치 Preview만 새 커밋으로 배포하고 브랜치 전용 테스트 GAS URL·비밀값 설정을 확인한다. 새 Preview URL을 호스트 스크립트에 고정한 뒤 사용자에게 재시험 준비 상태를 보고한다. 실제 25명 재시험은 자동 실행하지 않는다.

## 장애 복구와 한계

쓰기/flush 예외 또는 실행 강제 종료 시 소유권은 자동 만료시키지 않는다. 늦게 끝나는 이전 실행과 새 실행이 같은 행을 동시에 수정하는 것을 방지하기 위해서다. 해당 학생은 LOCK_TIMEOUT을 계속 받을 수 있다. 관리자는 먼저 유입을 멈추고 Apps Script 실행이 모두 종료됐음을 확인한 뒤, 해당 행의 payload/저널을 확인하여 해당 `submissionOwner:v2:*` 속성의 owner만 비우는 수동 복구가 필요하다. 학생 이름·저널·비밀값을 로그에 출력하지 않는다. 자동 복구 기능은 이번 변경에 포함하지 않는다.

PropertiesService 용량/일일 호출량, Sheets 지연, Apps Script 동시 실행 제한은 별도 위험으로 남는다. 이 방식이 실제 25명에서 충분한지는 재시험으로 확인해야 한다. 물리적 행 쓰기의 서비스 장애까지 데이터베이스 트랜잭션 수준으로 보장한다고 주장하지 않는다. 불확실한 쓰기는 재진입을 차단해 보수적으로 처리한다.

Vercel은 허용 목록의 안전한 code와 LOCK_TIMEOUT의 Retry-After: 1을 전달한다. 브라우저와 호스트 스크립트는 동일 직렬화 body/requestId로 502/503/504만 최대 3회 시도한다. Retry-After와 500ms*2^attempt + 0~300ms jitter 중 큰 값을 사용하며 15초를 초과하는 대기에는 재시도하지 않는다. 호스트 보고서는 최초·재시도를 구분하고 응답 본문/이름/쿠키/인증 헤더를 저장하지 않는다.
